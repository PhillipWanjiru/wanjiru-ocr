# Lab note: what the independent checks found

Started 2026-10-29; later entries carry their own dates. A lab note records experiments and what they
showed, including the ones that showed the author was wrong. Entries are added, not rewritten. Contracts and
ADRs cite this file by name.

Contents: 1. a tie in number formatting; 2. how often the intervals contain the truth; 3. the mutation
check; 4. what a stored `f32` costs; 5. which pixel-centre formula; 6. a budget that was missed;
7. what none of this shows; addenda: A1. a stack overflow in the YAML reader; A2. the registries read the same
by two readers.

## 1. A tie in number formatting (2026-10-29)

**Question.** DocIR is hashed over RFC 8785 canonical JSON, whose numbers are written the way ECMAScript's
`Number.prototype.toString` writes them. Does the Rust formatter agree with it on every `f64`?

**Method.** Compare `wanjiru-docir`'s canonical form with Node.js (`tools/oracles/jcs.js`), which is an
ECMAScript engine, on the number table in RFC 8785's appendix and on a generated corpus of 15,383 doubles:
random bit patterns of every exponent, short and long decimals, powers of ten and their neighbours, subnormals,
and deliberate exact ties. The corpus is committed as `crates/wanjiru-docir/tests/golden/numbers.txt`, so the
Rust tests need neither Python nor Node.

**Result.** One disagreement, on a value from the RFC's own list: the double `0x4314_3ff3_c1cb_0959` is exactly
`1424953923781206.25`. The shortest digits that read back to it are 17 long, and two candidates, `...206.2`
and `...206.3`, are equally close to it. ECMAScript takes the even candidate, `...206.2`; Rust's `{:e}` rounds
the tie up and gives `...206.3`. The Rust unit tests had passed; the comparison with Node found it.

**Fix.** `canonical.rs` re-rounds the exact value to the same number of digits when a tie is possible (a value
with at most 25 fractional bits and at least 15 digits), and keeps the result only if it still reads back to
the same double. The RFC vector is now a unit test, and the Node comparison is the committed golden file.

**Reading it.** A one-digit difference in a number would have changed a hash, which is the only thing
canonical JSON is for. It was found because an independent implementation was asked, not because the code
looked wrong. This is the reason ADR-005 requires an independent oracle for every special function and format.

## 2. How often the intervals contain the truth

**Question.** `wanjiru eval` reports 95 % intervals by a bootstrap over documents. Of many golden sets drawn
from one population, do 95 % of the intervals contain the true error rate? An interval that covers 88 % of
the time is a wrong interval with a confident label.

**Method.** `crates/wanjiru-eval/tests/coverage.rs`. The population is made to resemble recognition errors:
log-normal document lengths (median 250 characters); 10 % of documents "hard" with a per-character error
probability of 0.06 and the rest 0.002, so the true rate is exactly 0.0078. Per cell: 4,000 corpora, 1,000
resamples, seed 7. The run is deterministic, so the table is exactly reproducible.

**Result.** Coverage of the nominal 95 % interval. The table was first measured in Phase 1 and run again on
2026-11-04; the two runs agree in every cell to the three decimals shown:

| documents | bootstrap-t (the default) | percentile |
|---|---|---|
| 50 | 0.957 | 0.883 |
| 100 | 0.971 | 0.917 |
| 200 | 0.961 | 0.927 |
| 360 | 0.953 | 0.932 |
| 1000 | 0.950 | 0.943 |

Each cell is an estimate from 4,000 corpora and carries a standard error of about 0.003 to 0.005, so a
difference of less than about 0.007 from 0.95 is not a difference.

**What it shows.**

- The percentile interval under-covers at every size: by about 7 points at 50 documents, 3 at 100, 2 at 200
  and at 360, and 1 at 1,000. This is why the studentised interval is the default.
- Bootstrap-t is conservative up to 200 documents (too wide: its intervals are honest and wasteful) and
  within the noise of nominal from 360 on.
- It depends on the population. The same comparison in Python (NumPy, 1,500 corpora per cell, 500
  resamples, per-document error probability Beta(a, b) with mean 0.02, `cov_sim2.py` in the author's
  scratch space, not committed):

  | population | documents | bootstrap-t | percentile |
  |---|---|---|---|
  | Beta(0.5, 24.5), heavy tail | 100 | 0.934 | 0.907 |
  | | 360 | 0.946 | 0.940 |
  | Beta(2, 98), light tail | 100 | 0.928 | 0.926 |
  | | 360 | 0.943 | 0.943 |

  At 100 documents bootstrap-t is conservative in one population and slightly short in the others. At 360 it is
  within a point of 0.95 in all of them. How an interval at about 100 documents behaves depends on how heavy
  the tail of the errors is, which nobody knows before the first real corpus is measured.

**Consequences.** The golden-set plan asks for about 360 documents per class. A short corpus gets the
verdict `inconclusive` and not a verdict from a point estimate. The default test asserts that bootstrap-t
covers between 0.935 and 0.965 at 360 documents (1,500 corpora).

**Not shown.** Three populations. Real recognition errors have structure these do not (one bad font, one bad
scan session), so the interval's behaviour on the real golden set is a question for the real golden set.

## 3. The mutation check (re-run 2026-11-04)

**Question.** The evaluation harness decides whether the engine meets its contracts. If it contained a bug,
would any test notice?

**Method.** `tools/oracles/mutants.py` plants 17 deliberate faults one at a time in `wanjiru-eval` (a missing
`n/(n-1)`, the wrong MRZ check-digit weights, a leap-year rule, a strict instead of non-strict boundary, a report
member wired to the wrong counter, and so on), runs the whole test suite, and records which tests failed. A
fault that nothing notices is a *survivor*. A fault whose pattern is no longer in the source is *stale* and
fails the run, so the list cannot rot.

**Result** (on the final sources, about 53 seconds):

```
17 faults: 10 killed by unit tests, 7 killed only by the oracle comparison, 0 survived, 0 stale,
0 did not compile, 0 unattributed
```

The seven that only the independent Python implementation caught are mostly statistical: the standard error
without the small-sample correction, one-sided quantile levels, an interval that is not reflected, empty
resamples not skipped, a paired comparison on the same random stream, a p95 computed at 0.9, and a report
member wired to the wrong counter. The unit tests did not catch them; the comparison of whole reports and
intervals against an independent computation did.

**Reading it.** The oracle earns its place. A first version of the script reported one stale fault (a pattern
broken by a line wrap from `cargo fmt`); the pattern was fixed, and the script now fails on stale entries.

## 4. What a stored `f32` costs

**Question.** DocIR stores coordinates as `f32` and computes with `f64`. How far from the truth can a point end
up after a round trip through a transform and its inverse?

**Method.** Tests in `crates/wanjiru-types/src/geometry.rs`: 100,000 random affine maps (rotation, anisotropic
scale with condition number up to 50, rotation, translation up to 5,000 px) and random points in
[0, 8,000] px, forward then inverse.

**Result.**

- In `f64`: worst displacement below 1e-6 px.
- With the mapped point stored as `f32`: worst displacement below 0.05 px. The cause is the rounding of a
  stored coordinate, about 6e-8 times its size (2^-24), amplified by the condition number of the inverse; the
  rough size is `6e-8 x |p| x condition`.
- For chains of projective steps in `wanjiru-docir`, about 1e-6 px for coordinates up to 10^4 px while the chain's
  condition number stays below 10^3 (`docir/src/transform.rs`).

**Reading it.** 0.05 px is a small fraction of one pixel, so `f32` storage is safe for the polygons. It is not safe for the intermediate values of a long chain, which is why the arithmetic is `f64`
and only the stored result is narrowed (ADR-004, which names 0.05 px as the yardstick that would trigger a
rethink).

**Not shown.** Maps with a condition number above 50 for affine and above 10^3 for projective chains, and
coordinates beyond 10^4 px. The contracts state those limits; nothing above them is promised.

## 5. Which pixel-centre formula

**Question.** The blueprint writes the resampling map as `x_src = (x_dst + 0.5) / s - 0.5`. The code
multiplies. Which is right?

**Answer.** Both, in different coordinate systems. In *index space*, pixel `i` sits at the integer `i`, and the
map needs the half-pixel shifts. In *continuous coordinates*, pixel `i` covers `[i, i+1)` and its centre is at
`i + 0.5`, and the map is a plain scaling. The code uses continuous coordinates throughout
(`wanjiru-types`, crate documentation), and the unit test `pixel_centre_scale_map` shows that conjugating
the scaling by a half-pixel shift gives the blueprint's formula. The centre of destination pixel 5 at scale 4
is at 5.5, lies in source pixel 1, and sits at source coordinate 1.375. Index-space formulas must not be
copied from the blueprint into code without the conversion.

## 6. A budget that was missed (2026-11-04)

`B-docir-01` asks for parsing, validating and canonicalising a 1 MB DocIR document in under 20 ms. Measured on
an idle machine: 23.62 ms (three runs: 23.32 to 23.94). It is a miss and is recorded as one, with the stage
breakdown and the next steps, in `docs/budgets.md`. The target was set before any measurement and is not changed.

## 7. What none of this shows

- **The oracle and the implementation share an author.** Python, Node and NumPy do not share code with the
  Rust crates, and that is why they found things the unit tests missed. They do share a head: a
  misunderstanding of a standard would be written into both. A reviewer who did not write either is still the
  strongest check that is missing.
- **Mutation testing finds only the faults it plants.** Seventeen faults chosen by the author say that those
  seventeen are covered. They are not a measure of coverage.
- **The simulations use invented populations.** They show how the method behaves in three worlds, not in
  the real one.
- **The sandbox is not the reference machine.** Timings and anything about speed need the machine fixed in
  Phase 10.
- **No OCR exists yet.** Every number in this note is about machinery: geometry, formats, maths, the harness.
  None of it says anything about how well the engine reads a document, because there is no engine.

## Addenda

### A1. A stack overflow in the YAML reader (2026-11-05)

**How it was found.** By checking a sentence. While writing `SECURITY.md`, the claim that all three readers
bound their nesting was tested against a crafted file instead of being believed. The JSON reader refuses
nesting deeper than 128 (`MAX_DEPTH`). The YAML reader of the quality contracts did not: a contract
containing `a: ` followed by 200,000 `[` and 200,000 `]` aborted `wanjiru eval contract` with a stack
overflow (exit 134). Deeply indented block mappings and sequences recurse the same way.

**Why the tests had not found it.** Every YAML test used input a person would write. Nothing had asked what
the reader does with input a person would not.

**Fix.** The reader threads a depth through its block and flow parsers and refuses nesting deeper than
`MAX_DEPTH`, with the same limit as the JSON reader, so that anything it accepts the canonical writer can
also write. A test checks the boundary exactly (128 nested collections accepted, the 129th refused) in
flow, block and sequence style, and that 200,000 brackets and 1,000 indented levels are errors. At the
command line the three crafted files now give `WNJ-E4001 ... nesting deeper than 128` and exit 2.

**Not covered.** A very long single line, or a very large file, is still read whole into memory. The contracts
are small files chosen by the person running the tool, and the worker's input limits are a Phase 2 contract.

### A2. The registries read the same by two readers (2026-11-04)

The registries under `data/registry` first listed their entries as a sequence of records, which the in-house reader
does not accept (sequences of mappings are outside its subset). They were rewritten as mappings keyed by
identifier, which also makes a duplicate identifier a parse error. The conversion was checked by loading the
old and the new files with PyYAML and comparing, and afterwards all seven YAML files of the repository (four
registries, three contracts) were read by PyYAML and by the in-house reader and the results compared as
JSON: identical. That comparison was a one-off run and is not a committed test; the committed cross-checks of
the reader are the random vectors in `crates/wanjiru-eval/tests/golden/yaml.jsonl` and the contract and
fixture reports.
